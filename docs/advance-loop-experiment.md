# L0 对照实验规程

> 类型：实验规程
> 状态：有效；判定线和任务集已冻结（2026-11-19）；已完成 135 次伪执行端试跑，已获授权启动真实模型实验
> 更新：2026-11-19（Asia/Shanghai）
> 适用：推进循环 L0 的假设验证；后续阶段的复测沿用本规程，另建任务集

本规程规定对照实验怎样准备、怎样运行、怎样评分，以及看到结果之前就定下的判定线。实验要回答的问题是：**最小循环能否让 `deepseek-flash` 在同一条提示词下接近强模型单次执行的质量。** 假设及其依据见[推进循环架构](advance-loop-architecture.md#hypothesis)；实验脚手架属于[实施指南](advance-loop-implementation.md#work-packages)的 L0-9，运行属于 L0-10。

## 1. 前置条件

- 实施指南的 L0-1 到 L0-9 已完成，自动测试通过；实验脚本已用伪执行端跑通全流程。
- 任务集已按[第 2 节](#task-set)建成并冻结。
- 本机的 DeepSeek Harness、所配置的模型接口、组 C 使用的强模型和执行端在开跑当天实际可用；版本和服务返回的模型标识已记录。不可用的组不运行，也不用别的模型代替。
- **用户已给出开工指令。** 实验调用真实模型，会消耗模型额度。开工之后全程不再要求用户操作。

预计的调用规模：组 A 45 个执行回合；组 B 最多 45 × 6 个执行回合；组 C 45 个执行回合。L0 没有模型角色，角色调用为零。金额无法预估，按用量已知和未知分别记录。

<a id="task-set"></a>

## 2. 任务集

### 2.1 组成

共 15 个任务，都是小型的真实开发工作：

| 类别 | 数量 | 例子 |
| --- | --- | --- |
| 修缺陷 | 5 | 某个输入下结果错误；边界情况崩溃 |
| 加小功能 | 5 | 给已有模块增加一个选项或一种输入格式 |
| 带测试的重构 | 3 | 抽出重复逻辑、调整模块边界，行为不变 |
| 代码与文档一致 | 2 | 按文档描述补齐行为，或按实际行为修正文档和示例 |

### 2.2 载体

- 每个任务有自己的小项目，互不依赖。项目用 JavaScript 编写，测试用 Node 自带的测试运行器，`package.json` 里的测试脚本是 `node --test`。
- 项目不依赖任何需要安装的包。这样工作区副本不需要安装步骤，检查只要求本机有 Node。
- 每个项目 5 到 30 个源文件，单个文件远小于 DSH 文件工具的 256 KB 上限。
- 参考解相对初始工作区的改动不超过约 150 行。任务要小到一个条目的规模。

### 2.3 每个任务的内容

```text
desktop-app/experiments/advance-loop/tasks/<任务标识>/
  task.json      任务定义
  workspace/     交给各组的初始项目，包含可见检查
  hidden/        隐藏检查，只用于评分
  reference/     参考解，只用于证明任务可解
```

`task.json` 的字段：

```json
{
  "id": "fix-csv-quotes",
  "title": "修复带引号字段的解析",
  "category": "bugfix",
  "prompt": "CSV 里带引号的字段如果包含逗号会被拆开，帮我修一下。",
  "visibleChecks": [{ "kind": "command", "name": "test", "program": "npm", "args": ["run", "test"], "cwd": "." }],
  "hiddenChecks": [{ "kind": "command", "name": "hidden", "program": "node", "args": ["--test", "hidden/"], "cwd": "." }],
  "timeLimitMinutes": 20
}
```

### 2.4 构建规则

1. **提示词。** 一两句用户口吻的话，只描述想要的结果。不提检查、清单、循环，也不提示实现方法。三个组使用完全相同的提示词。
2. **可见检查。** 放在 `workspace` 里，是项目自己的测试。修缺陷和加功能的任务，可见检查在初始工作区上必须未通过。重构类任务的可见检查在初始工作区上通过，作用是回归把关。
3. **隐藏检查。** 比可见检查严格：覆盖提示词的完整含义和可见检查没有覆盖的边界情况。重构类任务的隐藏检查验证结构上的要求。隐藏检查在初始工作区上必须未通过，在参考解上必须通过。
4. **参考解。** 必须通过全部可见检查和隐藏检查。可以用任何方式写成。它只用来证明任务可解，不出现在任何一次运行的工作区里。
5. **隔离。** 运行器只把 `workspace` 复制给各组。`hidden` 和 `reference` 始终留在任务目录中，不进入工作区副本、任务包或任何角色的材料。
6. **先写检查再运行模型。** 全部隐藏检查和参考解在任何模型运行之前完成。
7. **来源。** 任务取材于常见的真实改动，由实现方编写，不要求用户审定。不能根据某个模型的试跑结果挑选或修改任务。

### 2.5 冻结

任何模型运行之前，对 `tasks` 目录下的全部文件计算 SHA-256，写入 `tasks.manifest.json`，并把这份清单自身的哈希记入每一轮的结果。冻结之后任务集不再修改。确实需要修改时，形成新的任务集标识，此前的结果不与新结果合并。

首个任务集已冻结：[任务文件及摘要](../desktop-app/experiments/advance-loop/tasks.manifest.json)。清单 SHA-256 为 `333d664cafabcb4631404bb38b17832222616cf60da0566b528e303b9c8f2a69`。可在 `desktop-app` 使用 `node --import tsx scripts/loop-experiment.ts --verify` 重跑评分自检，`--fake` 启动全流程伪执行。真实实验用 `--live --authorized`；组 C 另需已验证的 CLI、强模型和可用于隔离目录的 Responses 端点，分别以 `--codex-path`、`--codex-model`、`--codex-endpoint` 指定。DSH 与 Codex 凭据只从约定环境变量读入隔离保管库。

补救分支使用[独立复测任务集](../desktop-app/experiments/advance-loop/retest-v2/tasks.manifest.json)，清单 SHA-256 为 `e66f98f9021fd43d25a6d79a0063218a8c6ce94d7c33e9a8cf34b0b1dd24cce6`，运行参数为 `--task-set retest-v2`。两轮结果分别报告。

## 3. 组别

| 组 | 执行端 | 模型 | 推进模式 | 得到的东西 |
| --- | --- | --- | --- | --- |
| A | DSH | `deepseek-flash`，强度 `max` | 单次，现有行为 | 提示词和初始工作区 |
| B | DSH | `deepseek-flash`，强度 `max` | 循环（L0 最小循环） | 同上；可见检查作为条目的检查 |
| C | Codex | 用户实际可用的强模型，按其常规用法 | 单次 | 提示词和初始工作区；执行端自带终端，可以自己运行测试 |
| D（可选） | DSH | 所配置接口提供的强模型 | 循环 | 与组 B 相同 |

- 组 B 的清单是单一条目，标题就是提示词，检查是任务的可见检查。循环预算固定为：执行回合 6，每个条目带证据重试 4，墙钟时间 60 分钟，单个检查超时 300 秒。
- 组 A 和组 C 沿用现有的单回合时间上限 20 分钟。
- 组 C 使用项目内写入的沙箱，网络关闭，与现有受限任务相同。
- C 组开跑前，固定原生命令必须能在项目沙箱写入标记，且只读写入和写入同一试验目录下的沙箱外标记均被拒绝；同一模型还须完成独立的受限写入回合。探针不计入评分。
- 组 D 用来区分“循环的收益”和“模型的收益”。接口不提供强模型时不运行。
- 三个组都不使用项目规则、记忆和附件。

<a id="run-rules"></a>

## 4. 运行规则

1. **次数。** 每个任务每组运行 3 次，每组共 45 次。
2. **顺序。** 先运行组 A 并核对[有效性条件](#thresholds)；满足后运行组 B 和组 C。
3. **独立。** 每次运行使用全新的工作区副本和全新的隔离数据目录，运行之间不共享会话、账本或文件。
4. **不干预。** 运行开始后不做人工操作；循环组全程没有确认步骤。
5. **并发。** 同时进行的运行不超过 2 个，避免限流造成的差异。各组尽量在相近的时段运行。
6. **基础设施失败。** 模型服务不可用、执行端无法启动这类与模型输出无关的失败，这次运行作废并重跑一次；仍然失败则计为失败。作废的运行保留记录。
7. **超时。** 到时间上限仍未结束的运行计为失败。
8. **全部报告。** 每一次运行的结果都进入统计，包括失败、超时和用量未知的运行。不挑选样本。
9. **凭据。** 脚本从指定名称的环境变量读取密钥，写入隔离数据目录的保管库；密钥不打印、不写入结果。
10. **中断与续跑。** 同一轮只允许一个运行器。经确认原运行器已结束后，`--resume <轮次目录名>` 重用已落盘的运行结果；没有结束证据的尝试保留为基础设施中断，在独立目录按第 6 条最多补跑一次。续跑核对原任务集和配置，不跨轮合并结果，重读较早组时不得覆盖包含更多组的已落盘摘要。若原目录未列出组 C 的手动模型 ID，只能用该同一模型的独立原生成功样本补证；该样本不计入对照。
11. **评分恢复。** 执行端确认停止后，先记录执行结果，再从隔离评分副本运行检查。有执行结果而评分尚未结束时，续跑只重做评分，另建评分副本，不重新派发模型。即使执行超时，仍校验受保护文件；仅评分检查返回超时也算该样本失败，并保存分类，不伪造结果。

<a id="scoring"></a>

## 5. 评分

每次运行结束后，评分脚本按固定步骤处理，三个组完全一样：

1. 把运行结束时的工作区复制到评分目录。
2. 用任务初始工作区里的原件覆盖可见检查文件和 `package.json` 的脚本部分。这样对检查的任何改动都不影响评分。

3. 把隐藏检查复制进评分目录。
4. 用 L0 的检查运行器运行可见检查和隐藏检查。
5. 可见检查和隐藏检查全部通过，这次运行记为通过。

补救轮的评分副本也排除本轮新生成的检查文件，避免实验组自身的验收标准混入所有组共同的冻结评分。只排除初始工作区没有、且已被循环记录为采纳的检查；另外核对该文件是否缺失或被改写。原工作区、内部验收结果和检查输出仍完整保留。

指标定义：

| 指标 | 定义 |
| --- | --- |
| 通过率 | 一个组里记为通过的运行数除以该组的运行总数 |
| 失败率降低 | （组 B 通过率 − 组 A 通过率）÷（1 − 组 A 通过率） |
| 机制性虚假完成 | 只统计循环组。循环把条目标为通过，但第 2 步之后可见检查未通过；或运行结束时某个受保护文件与原件不同。两种情况各计一次 |
| 隐藏检查差距 | 系统判定完成的运行中，没有记为通过的比例。组 A、C 的“系统判定完成”指回合正常结束；循环组指循环以完成收口 |
| 执行回合数 | 每次运行派发的执行回合数 |
| 墙钟时间 | 从创建任务到收口、停止或回合结束 |
| 已知用量 | 服务返回的 token 用量；没有返回的运行计入“用量未知” |
| 被拒绝的写入 | 只统计循环组。文件工具拒绝的写入次数 |

## 6. 判定线

判定线自 2026-11-19 冻结。看到结果之后不修改；确实需要修改时，形成新版本的规程并重跑。

| 名称 | 条件 | 满足时 | 不满足时 |
| --- | --- | --- | --- |
| 有效性 | 组 A 的通过率在 20% 到 80% 之间 | 继续运行组 B 和组 C | 任务集过易或过难，不能区分各组。按同样的规则重建任务集后重跑；判定线不变 |
| 继续线 | 三项同时成立：失败率降低不小于三分之一；机制性虚假完成为零；组 B 单次运行墙钟时间的中位数不超过 30 分钟 | 进入 L1 | 按[第 7 节](#review)复盘，不建设后续阶段 |
| 支持线 | 组 B 的通过率不低于组 C 的通过率减 5 个百分点 | 假设在本任务集上得到支持；默认推进模式改为“循环” | 假设尚未得到支持；满足继续线时照常进入 L1、L2，完成后在新任务集上复测 |

说明：

- **为什么用失败率降低。** 它不受组 A 基础水平的影响。例如组 A 通过率为 50% 时，组 B 需要达到约 67%；组 A 为 30% 时，组 B 需要达到约 53%。
- **统计上的分量。** 每组 45 次运行，通过率的标准误大约是 7 个百分点，两组之差的标准误大约是 10 个百分点。判定线是事先约定的决策线，不是统计显著性的证明。
- **对外表述。** 达到支持线只说明假设在这个任务集上得到支持。要说“达到了强模型的质量”，需要在第二个独立构建的任务集上复现。
- **适用范围。** 任务集是无依赖的小型 JavaScript 项目。结论不能直接推到大项目、其他语言或界面类工作。

## 7. 没有达到继续线时的复盘

先看组 B 的失败属于哪一类，再决定下一步。每一轮重测都作为新的一轮记录，旧结果保留。

| 失败的主要形态 | 说明什么 | 下一步 |
| --- | --- | --- |
| 可见检查通过，隐藏检查未通过 | 检查信号不够，循环在一个偏弱的目标上收敛了 | 只实现 L1 中的角色端口、检查编写者和验证者（L1-1、L1-4、L1-6），在新任务集上按本规程重测 |
| 多次重试之后可见检查仍未通过 | 模型能力不足，或失败证据没有被有效利用 | 查看失败输出是否进入了任务包、文件编辑工具的失败率是否过高；修正任务包或工具说明后重测一次。仍然如此，结论是该模型在这类任务上不适用，停止 |
| 机制性虚假完成大于零 | 实现有缺陷 | 修复并补充测试后，重跑组 B |
| 时间超出 | 会话启动、限流或检查耗时过长 | 分段统计耗时，优化后重跑组 B |

## 8. 结果记录

每一轮实验的文件放在 `.dev/advance-loop/l0/experiment/<轮次>/`：

```text
tasks.manifest.sha256        任务集清单的哈希
environment.json             应用版本、DSH 与 Codex 版本、服务返回的模型标识、日期
runs/<组>/<任务>/<序号>/
  result.json                单次运行的结果
  state/                     这次运行的隔离数据目录，保留供复盘
  workspace/                 运行结束时的工作区
summary.json                 各组指标和判定线的结论
```

`result.json` 的字段：

```json
{
  "group": "B",
  "task": "fix-csv-quotes",
  "run": 1,
  "systemCompleted": true,
  "visiblePassed": true,
  "hiddenPassed": false,
  "passed": false,
  "mechanicalFalseCompletion": false,
  "protectedFilesChanged": 0,
  "executorRuns": 3,
  "rejectedWrites": 1,
  "wallMs": 412000,
  "tokensKnown": null,
  "infrastructureRetry": false,
  "timedOut": false
}
```

`summary.json` 给出每个组的运行总数、通过数、通过率、隐藏检查差距、执行回合数和墙钟时间的中位数，以及有效性、继续线、支持线各自是否满足和依据的数值。

- 结果文件只包含数量、布尔值、哈希和版本，不包含提示正文、模型回复或密钥。
- 隔离数据目录和工作区留在本机供复盘，不外发。
- 实验结束后，在[开发路线](roadmap.md)里新增一个带日期的小节，写明任务集标识、各组指标、三条判定线的结论、未运行的组及原因、已知的局限，并链接证据目录。

<a id="threats"></a>

## 9. 有效性威胁

| 威胁 | 应对 | 残余 |
| --- | --- | --- |
| 任务由实现方编写，可能无意中偏向循环 | 规则事先写明；任务集在任何模型运行之前冻结；每个任务有参考解和必须先失败的检查 | 无法完全排除，所以对外表述前要求在第二个任务集上复现 |
| 样本小 | 每个任务重复 3 次；报告全部运行；判定线明确不是显著性证明 | 结论的置信度有限 |
| 组 C 的执行端有终端，组 A 没有 | 这是有意的：组 C 代表“强模型按常规用法能达到的质量” | 组 A 与组 C 的差距里混有执行端的差别；可选的组 D 用来分离 |
| 隐藏检查本身写错 | 隐藏检查必须在初始工作区失败、在参考解上通过 | 可能过严，把正确但写法不同的实现判为失败；复盘时抽查 |
| 模型服务随时间变化 | 记录服务返回的模型标识和日期；各组在相近时段运行 | 不同轮次之间不可直接比较 |
| 任务形态单一 | 明确限定适用范围 | 不能推到大项目和界面类工作 |

<a id="later-stages"></a>

## 10. 后续阶段的复测

- **L1 之后。** 按第 2 节的规则另建 `l1-followup`，重复组 A、B、C。组 B 只收到与 A/C 相同的提示词及工作区，自行定约、发现检查及独立验证；不预填条目或检查。沿用 8000 的 A/B 执行输出上限、第 3 节的执行预算及默认 200 次角色调用上限。继续线和支持线不变；组 B 的运行期间用户操作请求必须为零，摘要记录其数量。用 `--task-set l1-followup` 运行或续跑。
- **弱信号补救复测。** 使用独立的 `retest-v2` 任务集。组 B 使用已完成的先失败检查和独立验证，暂不加入自动定约、并行候选或学习。根据首轮回执中的输出截断，DSH 的 A/B 两组选相同的执行回合输出上限 8000；C 组仍按 Codex 原生常规用法运行。其它运行条件和判定线保持冻结。用 `--task-set retest-v2` 运行或续跑。
- **难度复测。** `retest-v2` 的 A 组为 39/45，超出有效性上限，B/C 没有开跑。按第 6 节重建独立的 `retest-v3`；它增加需要同时处理多项边界的实际工作场景。继续运行时保留 8000 输出上限、原计分与原判定线。
- **L2 的埋入缺陷评测。** 取 5 个已有参考解的任务，在参考解上各埋入 3 个类型不同的缺陷：一处没有接入的功能、一处边界错误、一处与提示词不符的行为。以埋入缺陷后的项目作为“已完成”的起点运行找问题和分诊。指标是：埋入的缺陷进入清单的比例，要求不低于一半；进入清单的发现证据全部核对通过；超出目标的发现执行次数为零。计分时结论须匹配缺陷类型，且有实际变异位置的引用或能单独指明该缺陷的失败检查输出；只匹配标题不能计入。每条发现至多计一个未计过的缺陷。分类规则在 L2 真实运行前冻结。
- **L3 的回放集。** 取 L1 复测中受阻的条目，固定为回放集，比较有无升级阶梯时的解决比例。
  2026-11-20 冻结为 B 组已封存账本中的 22 条实际受阻条目（19 个样本），全量使用，不按隐藏检查得分挑样。两组在独立目录从同一已封存交付开始，使用相同的任务原话、失败说明、授权检查、模型和最多四个执行回合。旧实现可用普通重试；新实现用第一次失败后的升级阶梯，两组限时相同；顾问默认留空。主指标要求该条目取得原有等级的独立通过证据、原可见检查通过且保护文件未变；已经通过冻结隐藏检查的输入不得倒退。隐藏检查结果另列，不能用主指标声称全部隐含要求已通过。一次完整配对只占原定两个试验槽；必须有 22 个配对结果才判定是否提升。完成的结果原样复用；中断但无终态的执行保留并记为无效，不重派。
  当天首个完整轮次未通过。复测仅修正对照的普通重试次数：两组统一使用产品默认的 `retries=2`，升级组在相同的重试耗尽或无进展条件后才进入诊断。保留上述 22 条、两份二进制、每组最多四回合、模型、8,000 输出上限、其他预算和原判定线。它验证同一普通重试基线之上加升级阶梯的效果；不能同首轮样本合并。样本的工作区不含 Git 元数据，且全量均为评审条目，不能用此轮结果替代隔离并行、拆分、顾问的各自实测。
- 每次复测都按第 8 节的格式记录，并在开发路线中单列。
