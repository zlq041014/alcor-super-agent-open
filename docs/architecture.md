# 架构入口与实施基线

> 类型：项目架构导航与实施范围
> 状态：手机总管核心跨端路径已在真机验证；0.2.1 Windows 已切换为本机日用版；附件扩展单独验收；手机个人助手为下一阶段设计，尚未验收
> 更新：2026-11-25（Asia/Shanghai）
> 适用：星引 Alcor Android 总管、Windows Hub、Codex 与 DSH 连接器

## 当前架构：一个总管，手机回答，电脑执行

[手机总管首版设计](mobile-manager-v1.md)是此次转向的主要维护位置。用户从同一入口对话、开讨论或找回已有会话；手机保存讨论和待发授权，直连 DeepSeek 完成对话、搜索和文本制作。目标电脑的 Hub 继续掌握原生执行权，接收已配对手机的命令，按原有项目与会话绑定派发一次，再把有证据的状态和结果同步回来。总管即时反馈不依赖桌面响应，缓存或中继送达不能证明执行开始。

0.2.1 的桌面入口只监听操作者选中的局域网地址。设备授权、请求与回执保存在桌面数据目录的 `mobile/` 独立账本；主账本恢复不会使旧手机请求重新派发。手机同步讨论使用来源身份与消息编号，回执使用独立事件序号；两端都保留来源和缓存缺口。

新主线复用桌面的讨论、单次派工与任务管理，以及迁入手机工程的会话归属和同步基础。既有循环的维护与历史回放仍按创建时的约定；停止以团队循环胜过单人为新功能目标。桌面交付和实验证据不计入[手机首版验收](roadmap.md#mobile-manager-v1)。

**下一阶段（2026-11-25，尚未验收）。** 用户确认把手机端扩为个人助手，设计见[手机个人助手](mobile-assistant-v2.md)。本页描述的仍是已实现的架构。新增能力中，M1 笔记的文字记录、收件箱、检索、转对话和本地导出已实现；记忆、提醒、工具循环仍未实现。这些能力只在手机上运行，手机直连模型的做法不变。Hub 掌握原生执行权、状态以回执为准的边界也不变：模型不能把「交给电脑」当作工具自行调用，仍由用户在交接卡上授权。需要 Hub 配合的只有两项，均未实现：面向已配对手机的 Agent 结构只读查询，以及跨网络转发。

手机端的代码分层、目录、数据归属、桥契约和开发规范见[手机端代码架构与开发规范](mobile-code-architecture.md)。当前按“成品可用 → 交互流畅 → 还原原型 → 代码可维护”的顺序推进；测试和规则按风险取舍，不追求全覆盖。

## 已交付桌面基线

2026-11-19 用户确认在保留 Codex 的基础上兼容 DSH。0.1.8 的总管、讨论及新执行节点统一默认 **自定义 API · `deepseek-flash / max`**，每个节点仍可独立调整。可以显式改用 DeepSeek 官方 Key；官方模式固定使用官方 HTTPS Chat Completions 地址。保存的自定义端点和协议可在切回时继续使用。

实施采用 Electron + TypeScript、独立 Node.js Hub、SQLite 的本地模块化架构。模型提出理解、计划与验收建议；Hub 保存任务事实、核对授权、派发与恢复；连接器处理原生协议。简单任务由执行者兼任负责人，多任务协作按需增加负责人调用，状态与停止操作走程序路径。

新工作默认使用 DSH；创建卡片固定执行端，旧任务及原始 Codex 会话保留归属。DSH 按任务启动隔离 ACP 进程，经握手核对模型和强度后才发送任务。Hub 为该进程临时提供回环模型通道和限定项目的文件工具，两者分别鉴权，供应商 Key 只留在 Hub。文件工具只接受项目内相对路径，不跟随链接，按只读或项目写入授权。旧文件授权路径不开放终端、外网工具或子代理。普通原生循环及新建成果图使用 DSH 原生工具；图的只读与工作区写入授权分开，交付登记附加在原生会话上。各 DSH 角色继承 DSH 提供方的模型容量，试验观测不改写请求；已有 Codex 原生能力不变。DSH 的托管能力与 D2 整体放行分别见[开发路线](roadmap.md#first-release)。

Codex 原生接入：明确指定只读或项目内写入时，只有受支持协议版本的沙箱类型、网络关闭和唯一工作区根目录都与请求一致，Hub 才派发回合。项目写入还须明确排除临时目录，并拒绝额外写入根目录。缺失或不符一律记录并停止，不用请求值代替原生回执。明确沿用本机 Codex 权限的工作不套用这些受限模式条件。

原桌面控制通过原 owner。明确没有 owner 时发送未派发，可以在原桌面重新打开后再试；已发出但缺少匹配回合的收据时保留未知并禁止重发。独立进程读取的是已落盘历史，可能将原窗口还在运行的回合呈现为已中止，因此运行状态单独从原窗口的一次性只读快照取得。停止绑定观察到的原窗口与回合编号；请求回执和终止证据分别呈现。只有同一回合在原窗口快照中报告 `interrupted` 且窗口已空闲，才确认停止；独立历史及离线副本不能替代该证据。

由星引发出的 Codex 原窗口续聊在派发前持久占用授权目录。发送收据只能确定回合号，不能解除占用；需核对同一目录、会话及回合的原窗口终态。星引在重启后只读核对，不会重发；窗口不可达或没有匹配证据时保留占用。既有未包含目录占用记录的历史会话不会被批量标为活动。用户在原窗口独立发起的操作仍由原生端控制。

桌面控制管道握手返回客户端编号，没有桌面版本证明。操作回执必须匹配请求编号、方法与被发现的原窗口；无法发现原窗口或协议异常时，星引保留历史只读入口并说明原因，不凭握手标为受控续聊已验收。

原生端的目录列表和最近历史只在成功核对项目、会话绑定后保留本地副本。离线读取明确显示保存时间和截断边界，不能以缓存取得原窗口控制、确认未决回合或发起交接。历史检索只匹配仍在原授权项目和目录下的本地副本，结果显示保存时间。无缓存时提示不可用；会话或目录回执不符直接拒绝。

支持的 Codex 历史把发送的客户端请求编号保存为用户消息的 `clientId`，和消息项自己的 `id` 不同。星引只在会话和工作目录吻合、请求编号和原文 SHA-256 唯一匹配时补记丢失的发送回执。匹配到托管回合但仍无结束证据时，继续保留工作区占用，不派发第二次。原生停止按回合去重；只有 `interrupted` 证明回合已停止。

DSH 原生结束回执必须匹配本机隔离会话、工作区、发送正文与回合号。匹配后记录已知的终止分类；达到模型输出上限是本回合失败，会保留文件变更与终止原因供后续判断，不当作网络故障或成功收口。

DSH 会话保存在星引数据目录的 `dsh/` 下，与 DSH Desktop 自己的资料隔离。继续任务仅在端点、权限、工作区、模型与有效规则匹配时续接。原生模型或网络失败不转投另一服务；中断回执不确定时保留占用。核对只读本任务的原生结束记录，匹配会话、工作区与当次命令摘要，不能仅凭最后一条回复解除占用。私有思考内容不进入星引工作记录。

E1 的 DSH 原桌面接入只使用用户配置的 DSH Remote 桥。桥接令牌独立加密并绑定地址；不扫描本机端口或读取原桌面私有凭据。列表与历史须核对会话、目录和协议回执，离线副本保留原来源。手动续聊发往同一 Host 会话，带请求编号，沿用原会话的权限。成功状态码没有有效接收回执时，保留未知和目录占用；匹配原输入的回合结束后才释放，不自动重发。现有 `session/cancel` 只接受会话、不绑定回合，在接口升级前按回合停止保持不可用。

明确的项目决定进入规则账本，并保留讨论和用户原话引用；泛泛认可不自动保存为跨会话规则。原始讨论仍可查看，模型后续从当前生效版本读取决定；既有交接里的旧决定副本不再作为输入。待确认的讨论交接在规则版本变化后必须重新整理。恢复旧备份不会复活已删除的决定。

调度区分计算槽和工作区占用。原生明确等待答复、等待审批或结束状态未知时，仍占用原工作区，避免同目录重复执行；不占普通新任务的计算槽，独立项目仍可继续。停止、答复和核对不排入普通任务队列。

D3 先实现一次性预约继续。用户只能为已暂停且无活动或未知执行的工作预约，需开启后台保留。预约持久绑定时间、任务与清单修订、当前授权目录、模型和规则版本。到时只在仍满足预约条件和原有剩余额度时，将同一工作交回现有调度器；不会替换执行者、增加额度或放开目录占用。预约领取与任务转移在同一事务中提交。取消、修改授权条件或恢复备份会使未领取的预约失效。应用完全退出时不运行，重启超过预约时刻 15 分钟便标记过期；不设置系统计划任务或开机启动。

D3 的第一类推断偏好是总管答复详略。用户打开学习后，可对已完成的总管答复选择「更简洁」或「更详细」。单轮只算一条证据，可改投；通用对话和各项目独立。最近 60 天至少两轮同向且无反向证据才提炼为候选，不另发模型请求。候选由用户启用后才作为答复呈现建议；当前请求和明确规则优先，偏好不影响派发、权限、验收或额度。规则页可核对原答复、暂停、按作用域导出及删除。失效的偏好不随旧回复回灌；删除的证据不会从旧备份复活，恢复的偏好须重新启用。

D3 工作方法先从预声明文件验收的反复失败提炼。复盘问题按工作、修订和同一检查契约合并；事实关联失败回合，提议与未知原因分开，不另唤醒模型。候选记录已向执行者交付失败证据后，由同修订、同环境的执行回合通过原检查的恢复案例。另一项独立工作也须在相同项目、授权范围、检查契约、模型与连接器版本上独立复验，才有资格由用户启用。新版环境不沿用旧证明；已使用方法后仍未通过原检查时立即待重验。方法只提供核对顺序，不生成命令、不改变原检查或预算。保留原始工作和验收；删除方法同时屏蔽其历史派生证据，旧备份不复活。

系统通知由窗口针对已提交的回合或循环收口事件向 Hub 领取。回合按 Run ID、循环按清单修订和收口事件区分，重复事件及进程恢复不得重复领取。通知失败或关闭窗口不会更改任务结果和未读状态。

## 桌面基线的决定与验证记录

- **已确认要求：** 兼容 DSH 并保留 Codex；自定义 API 默认、可选官方 DeepSeek Key、全树默认 Flash/max、完整基础首版。
- **已确定实施设计：** 本地单协调 Hub、独立连接器、任务账本、显式状态与版本、分层验收、最小凭据传递、持久恢复；具体契约见上述入口。
- **待实测：** 所配置端点是否提供该模型及所需结构化能力、Codex 托管和已有桌面会话的兼容性、权限与停止效果、安装和资源占用。
- **交付与兼容边界：** DSH 原桌面已支持核对历史和续聊；现有 Host 的停止接口不带回合身份，精确停止仍由原桌面处理。答复详略和文件验收方法已经过留出复验；更广的偏好、方法类别、多设备接管及插件生态属于后续扩展。
- **已确认要求（2026-11-19）：** 循环运行时权限问题不影响运行，尽量不要求用户审批或中途确认。
- **历史实施设计（2026-11-19）：** [推进循环](advance-loop-architecture.md)逐阶段验收，默认仍为单次。各阶段的适用范围和后续 L4 验收见[路线图](roadmap.md#loop-l4-live)。
- **已确认的更新（2026-11-21）：** 新建的「循环推进」直接派发完整的原生 DSH Agent。执行和独立复核使用同样的原生工具，交接用自然语言。星引安排和记录回合，按真实原生回执处理暂停、失败和未知状态。旧循环保留原范围。
- **历史实验目标（2026-11-23，11-24 停止作为开发主线）：** 用同一提示词比较 DS 团队与单个 DS Agent，不引入强模型；开工前可先查找优秀案例和理论。
- **已实装到本机日用版（2026-11-23）：** 新建成果图可勾选在开工前制定质量标准，之后的制作、复核和收口都按标准卡逐维度对照。见[开工前定质量标准](native-loop-target.md#standard-first)；打包验证、日用切换和真实对照进度见[路线图](roadmap.md#standard-first)。
- **已确认并实现（2026-11-23）：** 用户确认自定义网关的 `deepseek-flash` 能看图。该路由在 DSH 模型声明中加入图像输入，原生 Agent 可用 `read_image` 查看工作中生成的图片；其他模型、官方 DeepSeek 路由和图片附件的处理不变。

API 模型名按用户要求保存。本轮经用户授权使用其指定凭据目录中的 GPT 配置，实际 Responses 请求返回 `gpt-6.1-sol`；真实 Key 仅瞬时处理并保存为用户级 DPAPI 密文，没有进入源码、文档或普通日志。Codex 原生提供商凭据单独保存、单独传递，未继承整套宿主凭据。

## 0.1.0 实现与设计边界

源码位于 `desktop-app/src/`：`shared` 定义 Zod IPC 契约和类型；`core` 维护状态转移与工作区冲突；`hub` 保存 SQLite 账本、调用总管、管理 DPAPI、调度、备份和恢复；`adapter` 对接 Codex stdio 与原 owner；`ui` 是 React 页面。未初始化 Git，也未改手机端源码。

当前实现的具体取舍：

- 主进程和 Hub 使用 Node IPC，不开放 TCP 端口；renderer 禁用 Node、启用 contextIsolation/sandbox/CSP，宿主校验发起窗口与主 frame。Hub 以规范化数据目录的散列取得独占命名管道，目录联接指向同一账本也只允许一个 writer；管道不承载业务请求。数据位置配置损坏或账本版本较新时明确拒绝启动，不切换空库。
- 独立 Hub 随 Electron 宿主保持后台运行；宿主断开时停发并请求停止，重开从账本恢复。它尚不具备脱离宿主常驻、自动重启连接器的完整监督能力。
- SQLite schema 1 采用类型化 JSON 记录表、关键事件、唯一请求收件箱和删除标记；关键状态/命令在事务中提交，FULL 同步、WAL。尚未引入 FTS；当前搜索按项目身份匹配本地总管、讨论和执行消息，旧账本的保存回复单独标注。
- 总管只返回经过运行时校验的建议；创建工作时明确项目、读写范围和交付依据。普通执行者可在范围内推进。用户确认足以判定完成的文件/文本检查可自动验收，失败后最多修正 2 次且不扩大总尝试额度；其余定性结果由用户针对当前版本核对。
- 总管向支持的接口请求 JSON。回复为空、截断或不符合建议格式时，在同一模型与强度下最多修正一次，分别保留调用结果和用量；网络或服务错误不自动重试，校验失败的建议不进入派工。
- 默认对原生 shell 请求只读或项目写入沙箱，网络关闭；批准原生单次请求必须关联当前版本、具体请求和用户动作，不能提升为永久规则。MCP/连接器的资源隔离不能由该 shell 配置推定。
- 同目录/嵌套目录写入串行；独立 Git worktree 或非 Git 输出目录支持并行。依赖按已验收版本交接，上游改要求会使下游旧验收失效。回合结束时记录可整合差异的版本，整合前同时核对原项目基线和隔离产物版本。Git 新增普通文件与已跟踪改动同批预检，不自动覆盖冲突；写入前拒绝不会遗留未知占用。写入后缺少确认时，原工作区保持占用，可用原项目基线、Git 双向预检或输出文件内容只读核对；证据不全不重派写入。
- 附件和产物保存内容哈希及不可变副本；原路径后续变化不抹掉旧结果，但会阻止旧结果用于当前验收。附件投递绑定本回合，记录文本截断、图片交接或二进制仅元数据；后端接收不作为模型已读取的依据。扫描上限及格式限制在界面和使用说明可见。
- 手机和桌面验收单次工作时，凭据绑定页面显示的回合、正文、差异和该回合的产物清单。Hub 读取文件核对后，再检查任务修订、当前回合和证据；内容相同的其他回合也要重新打开核对。手机仍提交原回执的证据字段，无需重新配对。
- 桌面定向成果单独入手机收件索引。确认时绑定一台已配对设备、其当前项目授权和已结束的成功回合；可带交付正文和明确选中的文本产物。原讨论和手机派工账本均不改动。手机按授权读取，授权被撤销或桌面从备份恢复后旧分享不再补取；已在设备上查看或另行导出的内容无法远程收回。
- 还原备份先核对账本与全量引用清单，再备份当前数据。副本只按内容地址导入，不覆盖同名文件。还原期间暂缓其它写入，业务记录和对应审计事件在同一事务中恢复。删除标记及已领取的通知合并保留，避免恢复旧档后重新注入已删规则或重复通知；恢复前的其它事件可从恢复前快照查看。
- 原 owner 协议按本机 Codex Desktop `26.1111.2228.0` 验证；[独立试验包通过原窗口续聊和停止](roadmap.md#d2-real-owner)，证据与托管线程续接分开。

详细迁入方案仍是目标契约；上面列出的实现边界不是对首版验收范围的静默删减。当前验证证据与待办统一维护在[开发路线](roadmap.md#implementation-evidence)。

2026-11-19 推进循环文档：先形成架构提案；随后用户委托决定并提出免确认运行的要求，架构文档据此改为已确定的实施设计，并新增实施指南、角色契约和实验规程。两轮都只改文档和导航，没有修改源码、运行测试或改变 0.1.8 的行为。原件、SHA-256 和校验结果在 `.dev/documentation-maintenance/2026-11-19-advance-loop-120756/` 和 `.dev/documentation-maintenance/2026-11-19-advance-loop-guide-133611/`。

0.1.7 将本机目录发现与 Codex 目录同步分开。Hub 持久保存用户选择的父目录，只枚举直属目录项；项目页、总管查询和讨论路由使用同一份项目账本。两种来源按真实路径在入账时合并，旧 ID、用户命名、移除标记和原生归属保留。同名由用户选择，失联不按名称自动换绑。发现不读取正文；查进度才按原有授权取证。创建仅接受用户的明确命令或表单：在实际父目录下非递归创建一个合法文件夹，同名不会覆盖。Everything 只接收经核对的文件夹清单；真实工作区和执行仍由原有边界管理。详见[项目管理与验收](roadmap.md#local-projects)。

总管聊天里的明确文件查找命令运行随包提供的开源 fd。搜索范围为用户在命令中指定的本机文件夹，或项目页已选的查找位置。按文件名/目录名匹配，不读正文、不跟随目录链接，不依赖 Codex 或模型。搜索结果不改变项目索引或执行端的读写授权。

总管可用 Windows 本机文件系统核对目录访问能力；用户指定实际目录时，可直接列出有限的直属项。Codex 项目目录和原生会话的离线状态不代表磁盘不可读。目录列表不读取文件正文，不改项目授权。

用户追问在本机项目目录里找时，先刷新已配置的查找位置，仅用刚核对过的目录和近期用户原话消歧。定位回合只返回路径；同名或无法确认时交给用户选择，不读取疑似项目的资料。

0.1.5 将聊天的界面响应与后台处理分开：提交事件立即在当前收件人的对话加入临时消息；Hub 在慢调用前将用户消息与相应草稿的清空一起提交。界面以收件人和请求编号匹配账本记录，相同文字不是去重依据。运行中工具回执仍以原生回合为准，网络不确定不自动重发。完成回调不再修改输入框或其他对话的草稿。界面统一以右侧表示用户发言、左侧表示 Agent 与系统；原生会话依据 owner 回执与轮次进行对齐，不因查看而重新派发。

0.1.4 的新要求取代早期的默认模型与审批策略。新委派先写待确认记录，用户提交模型和强度后才产生 Agent、Task 或原生回合；确认幂等，取消不派发，重启不自动批准。内置总管没有重复创建步骤。Responses 和 Chat 分别传递 `reasoning.effort` 和 `reasoning_effort`，Codex 在创建/续接线程与开启回合时明确传递节点模型及对应强度。设置变化不改变运行中回合的快照。新工作默认沿用原生有效沙箱并指定 `approvalPolicy=never`；明确只读、项目内写入及隔离工作区仍强制原沙箱边界，例外授权不会自动同意。旧任务的范围不在升级时扩大。不同于旧内置默认值的自定义模型保留。

2026-11-18 的 0.1.3：总管/讨论的显式调用与 Codex 原生事件使用共同的可见工作记录。事件绑定本消息或 Run 内的稳定操作 ID，开始、增量和完成更新同一条记录；Agent 回复和用户插话划分可折叠的操作组。总管的文件读取、Git/Codex 查证、模型调用和交接结论来自本轮实际调用。仅接收模型公开摘要与用户可见的阶段说明；不将模型私有推理、认证头、完整工具参数或原生 stderr 写入过程记录。文件行数优先从原生补丁核算，只有版本扫描证据时不猜行数。支持 Responses 公开事件流与普通 JSON 响应，未知执行回执不自动重试。

2026-11-18 的 0.1.2：用户确认以一条总管对话管理所有项目，深入讨论或介入执行才进入分支。右树的每个节点是实际受委派的 Agent，项目、任务步骤、工具调用不作为父节点。Hub 保存稳定 Agent 身份及委派方；讨论用项目内独立 GPT 上下文，执行沿用既有任务授权和原生回合，二者分别记录。UI 选中节点只改变阅读和发送目标，不改变正在运行的工作。关键结果和待处理请求回到总管。
